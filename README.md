## 0. 先看这个(结论摘要,5 条)
1. **年化(本金按 1000 万算)**:样本内(IS,到 6/30)**约 89–95%**,留出期(HO,7–10 月)**约 48–57%**。写成区间,不要只写 57%:57% 是"仓位可以在上限之上多停几小时"的乐观算法,48% 是"超限同小时全砍、按平方根冲击计价"的另一端(见 3.2)。
2. **不是 1000 万都在用**:平均实际占用资金 IS 约 712 万、HO 约 331 万;IS 里峰值市值约 1200 万,已超过 1000 万本金(浮盈使占用上升)。按平均占用算,HO 年化约 173%——这只说明资金没用满,不是"能赚 173%"(见 3.1)。
3. **和 v9 比**:同一环境下冻结规则更好(HO +16.9pp,区间 [+4.5, +30.7] 不含 0);对 v9 **原引擎**,两边都按 0.3% 成本算,HO 只差 +6.0pp,区间 [−19.4, +26.1] 含 0,**分不出高低**(见 3.3)。
4. **规模**:净利几乎不随本金变多,70M 时年化约变成 1/7(这条来自旧引擎、旧规则,只看量级;见 3.4)。**KuCoin 现货版**:HO 只有 3.6%,主因是 KuCoin 成交太薄(见 3.6)。
5. **风险**:HO 收益很集中(9 月占 HO 净利约 51%、前 5 个币占约 64%);成本是公开数据估算,不是我们自己的成交;HO 不是干净的样本外(见第 4 节)。建议先 50–100 万 USDT 小额实盘试 1–2 个月。

## 1. 一句话讲清楚策略

某个币的永续合约**资金费率为负**时,"没有现货(卖掉自己的库存现货) + 做多 1 倍永续"可以**每 8 小时收一次资金费**;代价是手续费、买卖冲击(滑点)、以及现货与永续的价差(基差)变化。我们用过去约一年的**小时级公开数据**,本金 1000 万 USDT,有库存、成交量、持仓量上限,**不选币**(信号来了就做),看这套规则回测能赚多少。

|---|---|---|

## 3. 各情景结果(年化 = 净利 ÷ 1000 万 ÷ 年数;"IS / HO")

### 3.1 主结果(第八轮,修复引擎;冻结规则 vs 其他规则;成本=cal)
| 规则 | IS 年化 | HO 年化 | HO 按峰值占用资金算 | 平均占用资金 IS / HO(万U) |
|---|---|---|---|---|
| **冻结:闸门 m=2 + X5/48h** | **95.2%** | **57.1%** | 91.0% | 712 / 331 |
| 闸门 m=2 + X5/24h | 95.0% | 55.0% | 88.3% | 632 / 303 |
| 旧闸门 m=3 + X5/24h | 91.0% | 57.3% | 118.9% | 536 / 271 |
| 无闸门 + X5/24h | 87.4% | 53.1% | 66.7% | 746 / 395 |

**怎么读"年化"的分母**(以冻结规则为例):年化 = 净利 ÷ **预留的 1000 万本金** ÷ 年数。实际占用:平均 IS 约 712 万、HO 约 331 万;峰值成本占用 IS 1000 万(被本金封顶)、HO 约 628 万;**IS 峰值市值约 1200 万,超过 1000 万本金**(浮盈撑大了占用)。若按平均占用当分母,年化 IS 约 134%、HO 约 173%——但这只是说明资金没用满(HO 约 1/3),不能当成"收益率";真实回报仍要按你实际预留多少资金来算。

不同成本假设下(冻结规则 IS / HO):cal 95.2 / 57.1;平方根冲击 y=1 94.2 / 56.4;固定每腿 30bp 104.9 / 66.2;order-book 乐观端 116.9 / 74.6。

### 3.2 降风险 bug 修复后的"两个边界"(请先读这条)
旧引擎在仓位超过成交量/OI 上限时"同小时全砍",这笔不受 pov 3% 约束,而且 30bp 情景下额外冲击根本没收,这是审计员发现的 bug。修复后**强制降风险**遵守 pov、分小时砍(只验证了这一项;正常出场是否守 pov 3% 取决于上游代码,本仓库未验证)。代价是仓位会在上限之上多停留几小时:**IS 13.8%、HO 18.9% 的持仓币小时超过成交量上限(最大约 12–15 倍)**(超 OI 上限的小时占比不到 1%)。所以**这不是"硬上限"**。给**两个边界**,真实值应在两者之间或更差:

| 口径(冻结规则,cal) | IS 年化 | HO 年化 |
|---|---|---|
| 遵守 pov(新默认,仓位会超限停留) | 95 | 57 |
| 同小时全砍 + 平方根计价(旧,假设市场能接住大单) | 89 | 48 |

**建议当作"IS 89–95%、HO 48–57%"这个区间来看。**

另外要知道:冻结规则(m=2、X5/48h)是在**修 bug 之前**的旧引擎上、用 IS 选出来的,**修好之后没有重新选择**;所以修复后的表现,不是"为新引擎挑过的最优规则"。

### 3.3 和 v9 比,更好吗?
**同一环境(币池 339,成本 cal)**:把 v9 的规则(入场 < −10bp、等 168h 才出)放进我们的引擎。下面第一、二行的"年化"与"差值区间"**用的是同一个 339 币池**(区间用 `code/r7_v9boot339.py` 重算,输出 `results/r7_v9boot339.csv`)。

| 比较 | IS | HO |
|---|---|---|
| v9 规则放进同一环境(339 币,cal)的年化 | 71.4% | 40.2% |
| 冻结规则 − v9 规则(同一环境,339 币,cal),pp [95%CI] | +23.8 [+16.9, +30.8] | +16.9 [+4.5, +30.7] |
| 冻结规则(**cal 成本**) − v9 **原引擎**(原参数、pov 20%、**30bp**、币池 267),pp | +17.9 [+11.5, +24.5] | −2.9 [−30.4, +18.4] |
| 冻结规则(**也按 30bp**) − v9 **原引擎**(30bp、币池 267),pp | +27.6 [+21.3, +34.4] | **+6.0 [−19.4, +26.1]** |

读法:
- **同一环境下冻结规则更好**,两个窗口的区间都不含 0。
- 对 v9 **原来的引擎**:第三行把冻结规则放在 cal 成本、v9 放在它自己的 30bp,两边成本口径不同;第四行两边都用 30bp 才是同口径。**无论哪种,HO 的差别区间都很宽、含 0,说不清谁更好**。
- **v9 没有在新环境里重新调参**,冻结规则的 m、出场确认是在这套环境里用 IS 选的,所以"同一环境"不等于"同等调参"。
- v9 自己的乐观版本没有拿来比:例如 v9 引擎把"自身冲击抬高费率"一项设为 0 时,HO 年化约 82%,比冻结规则 30bp 的 66.2% 更高(`v9cmp/out/v9_10M.csv`)。所以**不能说"全面优于 v9"**。
- v9 的 267 币池是事后挑的、参数在同一窗口里调过,冻结规则的选择方式不同,两边都不是真正的前瞻证据。

### 3.4 资金放大到 70M(容量;**第五轮,旧引擎 + 旧规则(m=3、24h 确认、`derisk_force=1`),不是冻结规则,也不是修 bug 后的引擎,只作量级参考**)
| 规则(30bp) | 10M:IS / HO 年化 | 70M:IS / HO 年化 | 净利(万U)10M → 70M(HO) |
|---|---|---|---|
| 自适应(m=3, 24h) | 108.1 / 69.9 | 15.5 / 10.0 | 228 → 228 |
| 固定 E7×X5 | 106.5(IS)/ 66.8 | 15.1 / 9.5 | 218 → 218 |

**净利几乎不变,年化大约变成 1/7**(本金放大 7 倍而净利不变,所以年化被除以 7——这是算术上的必然;真正的发现是"净利不随本金增加"):瓶颈是库存(约一半候选小时被卡)、pov 3%(约 35–45%)和成交量上限,**不是本金**。平均占用资金只有 270–730 万,其余基本闲置。结论:在这套约束下,容量大约就是 10M 量级;库存清单变大或 pov 放宽,容量才会变。

### 3.5 执行方式对比(第六轮,旧引擎 derisk_force=1;冻结自适应规则;IS / HO 年化 %)
| 执行方式 | 30bp 成本 | 平方根冲击 y=1 |
|---|---|---|
| 吃单(基准,pov 3%) | 106.1 / 65.2 | 84.0 / 46.7 |
| 挂单+吃单,成交率 30%(逆向选择按配对基差) | 94.1 / 57.5 | 82.8 / 48.1 |
| 挂单+吃单,成交率 60% | 101.6 / 62.1 | 90.8 / 52.4 |
| 挂单+吃单,成交率 90% | 107.2 / 66.0 | 96.9 / 55.8 |
| 挂单 90%,逆向选择按单腿绝对价格(保守上界) | 68.0 / 43.2 | 57.7 / 33.1 |
| TWAP 6h / 12h / 24h | 101.2 / 65.2、94.3 / 62.8、82.7 / 57.3 | 84.5 / 50.0、82.5 / 50.9、76.8 / 49.8 |
| VWAP 6h / 12h / 24h | 100.0 / 65.1、91.7 / 60.9、74.8 / 49.4 | 84.2 / 50.1、80.9 / 49.9、70.4 / 44.7 |

结论:**没有哪种方式稳定地比"吃单"好**。固定冲击下拆单不省钱、只会拖慢建仓;平方根冲击下挂单和拆单有些优势,但优势完全取决于"挂单能成交多少、会不会被逆向选择",这是小时数据**无法验证**的假设,需要小额实盘挂单实验。

### 3.6 KuCoin 现货 + Binance 永续(现货在 KuCoin 卖,永续在币安做多;第八轮,修复引擎)
| 版本 | IS 年化 | HO 年化 | 相对币安现货版 |
|---|---|---|---|
| 币安现货 + 币安永续(冻结规则) | 95.2% | 57.1% | — |
| **KuCoin 现货 + 币安永续(冻结规则)** | **19.6%** | **3.6%** | **−75.9pp / −53.6pp**(区间都不含 0) |

- 币种:339 个中保留 318 个(KuCoin 有同名对),丢 21 个。
- **主因不是价差,而是"能做多大"**:KuCoin 现货成交额只有币安的约 **2.6%(把每个币、每个小时的 KuCoin/币安成交额比值先取中位数,再对各币取中位数)**;**按总成交额加总算约 13%**。两种算法差别很大。成交量/pov 上限成为主约束,平均占用资金只有 IS 约 140 万 / HO 约 15 万 U。按占用资金算年化会高很多,但那只是极小规模,**不能外推到 10M**。
- 在 KuCoin 版里,冻结规则在 HO 上比 v9 规则略差(−2.7pp,区间 [−4.9, −0.5]);m=2 闸门的成本是按币安校准的,没有按 KuCoin 现货重新校准。
- 对成本几乎不敏感(费用 ×2、半价差 ×2 都只变 0.1–0.5pp),因为收益被容量限制而不是费用。
- 永续腿杠杆与假想爆仓(不追加保证金、按小时最低价)——次数为"币×回合":

| 永续杠杆 | IS 爆仓次数 | HO 爆仓次数 |
|---|---|---|
| 1×(全额保证金) | **0** | **0** |
| 2× | 43 | 3 |
| 3× | 156 | 29 |
| 5× | 356 | 93 |
| 10× | 566 | 163 |

(也就是说:3 倍杠杆时,IS 有 156 次、HO 有 29 次假想爆仓;2 倍时 43 次 / 3 次。)

→ 这个策略需要"随时能追加保证金的资金池",**不是靠杠杆省钱**。上涨端:个别币一个回合涨数倍,回补需要从币安划钱到 KuCoin(IS 峰值约占 10M 的 10–20%);KuCoin 的提币/划转时间与费用**没有建模**。

## 4. 风险与局限(引用任何数字前请读)
1. **HO 高度集中**:HO 约 **51%** 净利来自 9 月一个月(该月内年化约 115%);10 月**该月的年化**约 25%(10 月只占 HO 净利约 10%,**25% 是年化,不是占比**);**前 5 个币占 HO 净利 64%**,去掉前 5 币 HO 年化只剩约 **20%**(IS 去前 5 币约 61%)。**不要把 57% 当作稳态收益。**
2. **试了约 100 个出场变体,没做多重检验校正**;冻结规则在旧引擎下用 IS 选出,**修复引擎后没有重新选择**;HO 从第四轮起就被看过,所以**不是干净的样本外**。
3. **闸门的优势不稳,不能说"算过账所以更好"**:cal 成本下相对无闸门 IS +7.8pp [+3.2, +12.9];但 HO 上区间含 0(+4.0 [−6.7, +11.8]);在 30bp / 订单簿成本下优势消失(30bp:IS +0.1 [−3.0, +3.2];订单簿成本:IS −3.5 [−6.4, −0.5],反转);相对旧闸门 m=3 的 IS +4.2pp 区间也含 0 [−0.2, +8.8]。另外闸门估成本时始终用 cal 成本,换成本情景时闸门并没有"看到"新成本。
4. **成本是币安公开数据代理**(aggTrades 校准冲击;订单簿仅永续有,当乐观下界;现货沿用永续系数),**不是我们自己的成交**;现货半价差是静态快照;小时数据无法模拟小时内拆单和挂单排队。
5. 币池来自某一天的库存快照(事后选择);"去前 5 币"的排名是事后的;缺失小时的波动率用全样本中位数填补(略微非因果);KuCoin 的 318 币有幸存者偏差。
6. 第五、六轮(70M、执行方式)用的是**修复前的旧引擎**(70M 还用旧规则 m=3/24h),只能看相对关系和量级,不要和第 3.1 节的绝对数字混用。
7. **强制降风险**才验证了"不超过 pov 3%";正常出场是否守 3% 取决于上游代码(不在本仓库),**没有验证**;修复后仍有 13.8% / 18.9% 的持仓币小时超过成交量上限(见 3.2)。
8. 建议:先做 **50–100 万 USDT、1–2 个月的小额实盘试验**,用真实成交校准成本,再谈放大。

## 6. 怎么复现(诚实声明:不能一键复现)
本仓库**不含**下列输入,所以只能核对汇总表与代码逻辑,不能原样重跑:
1. 数据加载与上游规则模块(其中涉及私有库存处理);
2. 小时级数据集(币安公开数据构建;KuCoin 用 `kucoin/code/dl_kucoin.py`、`build_kc_ds.py` 自行下载构建);
3. **逐币库存/上限表**(私有,CSV 两列 `fut_symbol`、`cap_usdt`,环境变量 `NFB_HOLDINGS_CAP`;v9 对照用 `NFB_HOLDINGS_CAP_V9`)——是结果的关键输入,**你需要用自己的库存表,结果会不同**;
4. 成交过的币清单(`calib_dl.py` 的币清单文件,用你自己的币集合)、逐币校准表 `CALIB_DIR`、v9 仓库数据 `V9_DATA` / `V9_REPO`。

补齐后的运行顺序(路径由环境变量 `SIGNALS_ROOT` 等指定,默认当前目录):
```
python code/calib_dl.py bd <coins.txt>      # 订单簿校准
python code/calib_dl.py ag <coins.txt>      # 成交校准
python code/run_r7_is.py gate IS            # 第七轮 IS 闸门网格
python code/run_r7_is.py exits IS           # IS 出场网格
python code/run_r7_is.py exits HO           # HO 出场(各跑一次)
python code/run_r7.py                       # 第八轮修复引擎主表;NFB_DERISK=1 复现旧引擎
python code/r7_boot.py                      # 7 天块自助置信区间
python code/r7_v9boot.py                    # 对 v9 的区间(原引擎、币池 267)
python code/r7_v9boot339.py                 # 对 v9 规则同环境区间(币池 339)
python code/run_cap70.py                    # 70M 容量
python code/run_exec.py                     # 执行方式对比
```
